# 暖色卡牌 · 设计定稿

用户已选择：**B 的卡牌结构和交互，使用 C 的视觉 token**。这不是第四个候选方案，也不是把 C 的餐桌布局搬过来。本轮目标是把这套设计落到现有 Taro 小程序，直接展示运行效果。

## 1. 从这里看

- 唯一选定原型：`prototype/warm-cards/index.html`；`prototype/index.html` 指向此版本。
- 视觉 token：`prototype/warm-cards/tokens.css`。
- 原型样式与交互：同目录 `style.css`、`app.js`。
- 执行任务：`docs/WORKBUDDY_DESIGN_TASK.md`。

打开 HTML 即可演示；也可在仓库根目录运行 `python -m http.server 8791` 后打开 `/prototype/`。原型无需 npm、外部字体、图片 CDN 或 API。

桌面并列的三部手机是设计展示板，不是产品的三列布局。手机只展示一个页面；产品只保留底部“图鉴 / 点菜 / 采购 / 我的”。顶端角色切换、重置、空状态按钮是演示工具，不落入正式产品。

**视觉以此原型为准；业务仍遵守既定 PRD。原型里的菜名、数量、家庭成员、插画和固定推荐是样本，不是要硬编码进产品的数据。**

## 2. 保留什么，替换什么

保留 B：图鉴主卡与错位叠卡、轻触翻面、收藏编号、下一张、扇形菜单卡组、“抽一桌”灵感入口。卡牌是产品辨识度，不要退回普通表格或只有两列缩略图的首页。

替换为 C：明亮奶油底、森林绿文字、鼠尾草绿面板、陶土橘主按钮、柔和圆角、轻阴影、少量宋体标题。不要沿用 B 的深绿整屏底、青柠荧光色和丁香紫卡面，也不要引入 C 的圆餐桌、周历等新布局。

品牌仍叫“我的料理图鉴”。“暖色卡牌”是设计版本名，不要求产品改名。

## 3. 视觉 token

| 用途 | 值 | 用法 |
|---|---|---|
| 页面 | `#FBF8EE` | 奶油色全局底 |
| 卡片 / 表单 | `#FFFDF7` | 暖白，保留轻微层次 |
| 主文字 | `#254B42` | 森林绿，不用纯黑大块 |
| 次文字 | `#64796C` | 从 C 的灰绿加深，确保小字可读 |
| 弱装饰文字 | `#7F9386` | 只作辅助，不承载关键信息 |
| 选中 / 完成 | `#2D604E` | 绿色状态与图标 |
| 鼠尾草面板 | `#DCEAD9` | 人数配置、采购进度、选中导航 |
| 浅底 / 分隔线 | `#EDF0E4` / `#DAE3D6` | 控件与边界 |
| 主行动 | `#DD765D` | 陶土橘按钮；深色字 `#38271F`，不是小白字 |
| 卡牌补色 | `#F3D3BC` / `#F3EAD2` | 杏桃、米色，与浅绿组成卡组 |

标题用系统宋体/衬线 26–30px；菜名 20–23px；正文 12–14px；辅助 10–11px。正式小程序按设计宽度换算成 rpx 或等效尺寸，不必引入字体包。图标使用统一细线风格；不要用大 Emoji 替代食物封面。

参考尺度：页面左右 22px；卡牌圆角 20px、面板 18px、按钮胶囊；首页主卡约 252×292px，卡组高约 318px；叠卡轻微旋转约 -9° / +8°；软阴影，不加厚重黑边。**这是视觉标尺，不是要求逐像素照抄。** 小屏适配可自然缩放与微调，主要操作保持易点、易读。

## 4. 页面与关键交互

### 图鉴

上方标题、已收集数量、拿手菜数量；主体是一张突出菜品的收藏卡，后面两张错位卡作为层次。正面有编号、菜名、分类和制作次数，背面显示配方摘要；完整食材与步骤在详情里，不把长文塞进小卡。

主卡可翻面，另有“下一张”。掌勺者主按钮是“收录新卡”；家人不显示管理入口，可查看详情、收藏、加入点菜。下方保留少量收藏卡和全部图鉴入口；搜索、分类在浏览弹层里，避免第一屏堆满工具。

封面优先真实成品照，裁切以保留菜品为准；没有照片时使用明确的示意封面。不要求做自动抠图。原型 `assets/*.svg` 为可复用示意素材；正式运行不要让用户误以为它们是自己的成品照。

### 点菜

保留“抽一桌”的扇形卡组。先显示用餐人数、午/晚餐、家人的点菜心愿，再显示搭配结果和可替换的菜单列表。扇形卡仅预览，点击可看详情；不要求复杂物理轮盘、3D 引擎或无限抽卡。

“换一桌”是重新推荐，**不是直接确认**；优先保留已收到的家人心愿。家人主按钮是“提交我的点菜”，掌勺者主按钮是“确认菜单”。确认弹层能检查每道菜实际计划份量、去掉菜品，再生成采购清单。

人数只是配餐输入，不意味着菜数等于人数，也不意味着每道菜都必须做满同样份量。图鉴不足时，给新菜建议加“未做过”标记；经掌勺者确认配方才进入菜单，不自动进入已做图鉴。

### 采购

从已确认菜单生成；顶部显示进度，下面按食材类别分组。三种状态明确区分：待购、家中已有、已购买。点击用量可调整或查看来自哪些菜；家人只读，可复制待购清单，掌勺者能修改。

数量按每道菜的原始份量和本次计划份量换算，重复食材只做可靠合并。未知/适量仍保持提示，不能消失或伪造精确数。菜单修改后，旧清单仍绑定原确认快照；再次确认时提示差异，用量未变的保留勾选，有变化的重新核对，不静默覆盖人工修改。

### 我的

展示家庭、角色、收藏和制作记录即可。角色由真实登录关系决定，不把原型的“掌勺者/家人”切换器带进生产。不要为这轮视觉改造增加社区、等级、会员或家庭运营后台。

### 录入、详情与一张图

录入使用底部弹层，AI/手动两种入口。照片和描述 → 可编辑草稿 → 确认保存。未知用量留待补充，失败时保留输入；编辑已有菜谱更新原记录，不新增重复卡。沿用已有语音能力与状态；不要为本轮换肤另建语音服务。

详情聚合收藏、加入点菜、生成卡片和 owner 编辑。导出的菜谱长卡包含菜品图、菜名、份量、完整食材、完整步骤；内容多就增长画布，不能只导出封面或截断步骤，也不要带入应用导航和操作按钮。原型的“生成 PNG”有真实浏览器导出；微信相册权限与保存方式由运行端适配。

空图鉴给明确的首次收录入口；家人显示等待收录。加载、失败、无搜索结果、待核对用量使用同一套轻量提示。原型不假装真实 AI 返回或真实相册保存。

## 5. 实现自由度

可以复用并调整现有页面、组件、样式文件和服务层；组件拆分、目录、图标库、状态管理和 CSS 写法由 WorkBuddy 选择。不要为了贴合原型 DOM 重构现有工程。

3D 翻面在真机不稳定时，可用正反面切换加短淡入；扇形卡不必做物理动画。核心是保留卡牌层次、版式和语义。动画建议 180–300ms，减少动态效果设置下可关闭。

允许改善文案、间距、触控面积、裁切与安全区；关键色系、首页叠卡、菜单扇形卡、底部四导航、角色边界和采购规则不变。无需逐项提问，也不需要另写技术选型报告。

本轮沿用现有 Taro + Node.js + PostgreSQL + 对象存储；不要重新引入 CloudBase。真实 API 可用就接真实数据；缺少凭据时让明确的演示模式能跑通视觉闭环，并列出仅剩的外部依赖，不伪报真实联调完成。

## 6. 做完后给用户看什么

先启动实际小程序工程或其可运行预览，而不是只再交一个 HTML。给出图鉴、点菜、采购三张运行截图，展示一次翻卡、一次完整的点菜确认到采购流程，以及成员/掌勺者差异。

跑现有相关测试和小程序构建，修掉本次引入的问题。交付只需说明运行入口、提交、验证结果和确实存在的限制；不要求新增一套评审流程或长验收报告。

验收重点是：一眼能认出 B 的卡牌，一眼感到 C 的温暖；用户点击后不是一堆没有接通的按钮。原型已通过浏览器交互与 360/390/430px 布局检查，检查范围见 `prototype/warm-cards/checks.json`；这不等同于 Taro/后端/微信真机通过。
